DECISION 1. Where V2 published an error, does THO reproduce it or correct it?

policy

This unblocks the most work, and UTG has already answered it once by precedent — but answered it the other way somewhere else.

Chapter 2C table 0931 Temperature Units publishes three codes: degF (status D, comment “typo”), [degF], and Cel. degF is not valid UCUM — UCUM requires the brackets — so the chapter publishes a known-invalid code beside its correction, with two of three entries meaning Degrees Fahrenheit.

THO already fixed this. ValueSet/v2-0931 v2.0.0 carries only [degF] and Cel, and folds the history into the display text: “Degrees Fahrenheit (note that V2 has erroneously published this for many years without the square brackets).”

That is a good decision. We would like to know whether it is policy or a one-off, because our working default is the opposite — reproduce and record — and nobody has ratified it.

The counter-example, worth having in the room. Table 0560 Quantity Units is named for quantity, bound to ADJ-6, and publishes five codes of which four are units of time (HS Hours, DY Days, MN Month, YY Years). CodeSystem/v2-0560 in THO 3.0.0 publishes the same five. So here THO reproduced rather than corrected.

0931 and 0560 currently point in opposite directions. This is a live inconsistency inside THO, not an abstract question.

AskIs “correct in THO, record the history in the display text” the rule? If so we will apply it consistently and bring back the list of affected tables.

DECISION 2. Merge mechanics — we want a diff that shows only real changes

process

We would rather design for a reviewable merge now than retrofit one onto 800 resources.

Settled on our side. We will emit XML into UTG's layout (input/sourceOfTruth/v2/{codeSystems,valueSets}/), and match THO's existing serialization closely enough that a resource we do not change produces no diff at all — no reindentation, no reordered elements, no whitespace noise. The review should read “here are the N resources that actually change”, not “here are 800 files”.

We will enforce it with a round-trip test: take THO's existing v2 XML, run it through our writer untouched, assert the bytes come back identical. Anything that fails is a serialization bug, not a content change.

What we need from UTG is what we cannot see from the published package:

  1. Which UTG checkout should we diff against? We have hl7.terminology.r5 v7.3.0 (JSON) but not the source repo. We need the repo, and to know which branch is the right base.
  2. Are the conventions written down, or should we infer them from the existing files? Specifically element ordering, indent width, self-closing tag style, line endings, and whether the text narrative is hand-authored or regenerated by tooling. Narrative is the likeliest source of spurious diffs — a regenerated div touches every file while meaning nothing.
  3. What is the intake route — PR against the UTG repo, a proposal per resource, something else? And what proposal granularity does UTG want for a change set this size?

AskPoint us at the right UTG checkout and branch, and tell us how narrative is handled. Those two answers let us start generating.

DECISION 3. CodeSystem/conceptdomains — we are proposing 3.0.0 → 4.0.0

conceptdomains

Chapter 2C declares 760 distinct concept domains. THO 3.0.0 publishes 582 of them.

THO 3.0.0Proposed 4.0.0
Top-level concepts742919
Total concepts1,3451,522

The 177 additions are appended as new top-level concepts marked source: v2 — THO's own convention for v2-derived domains. Every existing THO concept is carried through unchanged with its hierarchy and properties.

Why a superset and not just Chapter 2C's 760. Publishing a subset at THO's canonical would destructively redefine a code system this project does not own: a server loading both packages would see concepts disappear.

Why not a supplement. A CodeSystem supplement may add properties and designations to an existing code system. It may not add concepts.

AskConfirm the major-version bump and the source: v2 marking, and that appending 177 top-level concepts is the right shape rather than slotting them into the existing hierarchy.

DECISION 4. Five concept domain definitions where Chapter 2C and THO disagree

0952, 0967, 0675, 0066, 0626

For 577 of the 582 shared domains the two agree word for word. These five do not.

Only 0952 is a near-match — it differs by formatting and a stray space. The other four are wholly different texts, which usually means the two bodies have attached different meanings to the same domain, not that one meaning is phrased two ways.

Our generator currently emits THO's wording. That was chosen when we assumed THO was the more reliable side; we now understand the existing THO v2 content to be less reliable than Chapter 2C in general, so we would rather not have picked a default by assumption.

Note this interacts with ask 1. If UTG confirms “correct in THO and record the history”, that is also an argument for Chapter 2C's wording winning here — which is the opposite of what we currently emit.

AskThese four need reconciling on the merits, not a tie-break rule. Choosing a wording does not fix a genuine disagreement about meaning.

THO GAP 7. Table 0459 is labelled as CMS content but does not look like CMS content

0459

Chapter 2C gives table 0459 Reimbursement Action Code the symbolic name cms-OCEEditCode-cs and OID 2.16.840.1.113883.6.301.9. Its four codes are 0– 3 with HL7-authored English displays — “OCE line item denial or rejection is not ignored”, and so on.

Those read as an HL7 enumeration about OCE behaviour, not as codes drawn from the CMS OCE Edit Code system.

AskIs the OID right? If these are HL7's own codes they need an HL7 code system, not a CMS one.

FYI 9. We are authoring at THO canonicals

Resources carry http://terminology.hl7.org/CodeSystem/v2-0nnn and ValueSet/v2-0nnn from the start, because the workspace exists only to be merged into THO. There is no interim canonical to migrate away from and no workspace-URL-to-THO-URL mapping for anyone to get wrong.

FYI 10. The output is not scoped to V2.9.1

V2.9.1 is the source being used to establish a correct v2 baseline, not the scope of the result. Resource version will not carry 2.9.1; Chapter 2C's “HL7 Version Introduced” becomes a concept property.

This pass is fidelity only. Substantive corrections to the v2 terminology are a deliberate second effort — keeping them separate is what will make the second one reviewable against this baseline.

FYI 11. Scale and method

Scale. 799 sections, 5,540 codes, 415 code-bearing tables, ~384 concept-domain-only, 760 concept domains.

Method. Two independent extractions of the same .docx — python-docx (character-faithful) and an LLM (structural corroboration) — agreeing on 740/799 tables, with every remaining difference classified and adjudicated against the source. Every change to published text is recorded with the decision that authorized it.

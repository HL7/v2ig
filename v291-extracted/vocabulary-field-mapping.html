Chapter 2C field mapping

What the chapter publishes about each table, and how much of it reaches the FHIR resources · 2026-08-25

Chapter 2C publishes far more about each code table than a CodeSystem and a ValueSet have room for. This document sets out, field by field, what reaches the generated resources and what does not — so that the information being dropped is dropped on purpose.

The question that prompted it was a narrow one: the Code System Identification block has a Full Name field, and nothing in the output appears to carry it. That turned out to be true, and to be one of twenty-four such fields. Two of them carry a value on all 799 tables.

This is the systematic version of what ADR-0008 calls Batch C — container-level metadata — which has been open since the ADR was written and lists four of these questions individually. Rather than answer them one at a time, the whole surface is laid out here with counts attached, so the ones worth spending effort on are visible next to the ones that are not.

Nothing here is a proposal. A field recorded as not carried is a question, not a defect: some of these have no sensible FHIR home, and some describe the chapter rather than the terminology. The purpose is to make the choice explicit.

What is not carried

Every field below exists in Chapter 2C and in none of the generated resources. The count is how many tables carry the field with a value in it. This is the decision list: for each one, either a way of preserving it is worth devising, or the loss is worth accepting on the record.

How the mapping changes with the output class

The mapping above assumes the ordinary case: a table that owns its code system. Most tables do not. Which fields have a destination at all depends on which of these classes a table falls into, and the counts are lopsided — the largest class writes almost nothing.

The external code system class is the one the original question pointed at. For those 24 tables Chapter 2C still publishes a complete Code System Identification block — OID, symbolic name, description, full name — describing a code system somebody else owns. We write no CodeSystem for them, correctly, so none of that block is carried, not just the Full Name.

The natural FHIR home for “here is what we know about a code system we do not own” is a NamingSystem, and THO already publishes those — that is how tables like 0227 were resolved in the first place. This project reads THO's NamingSystems and writes none of its own. So where Chapter 2C's description of an external code system differs from THO's, or adds something THO lacks, that difference is currently invisible. Whether it should be reconciled, and whether any NamingSystem should be authored here, is an open question this document does not answer.

The concept-domain-only tables

360 tables declare a concept domain and no code system, and 3 declare nothing at all. The mapping treats them almost entirely as a lost cause, because every block except Concept Domain is written for a table that has terminology. In practice the loss is much smaller than that suggests.

So the picture for concept-domain-only tables is not that 360 tables lose six blocks of content each. Nearly all of them carry the Concept Domain block and the table metadata block and nothing else, and the Concept Domain block is carried in full. What they lose is what every table loses: the table metadata. That matters more here than elsewhere, because for these tables the table-level Description is the only prose the chapter offers apart from the domain definition itself, and it reaches nothing.

The handful of exceptions are already known and already escalated. The two carrying a Code System block are 0560 and 0910, whose block is the noObject placeholder. The four carrying codes are the tables that publish example codes for a domain — conforming behaviour under the V3 requirements, and the subject of an open register item about where those examples should live.

Most of the seventeen are already-known defect classes appearing in a field nobody had checked — links to rendered pages where a canonical belongs, hl7.org/permalink addresses, and references to genuinely external value sets at FHIR or PHIN VADS canonicals. Those tables are mostly blocked already for other reasons.

Four of them are a real divergence, and they point the same way. Tables 0291, 0347, 0399 and 0834 print a canonical of the form …/ValueSet/v2-notAllCodes-NNNN — THO's convention for a value set that enumerates a subset of its code system rather than including all of it. THO and UTG both publish exactly that canonical, and neither publishes the v2-NNNN form we generate. So for these four, the chapter, THO and UTG agree with each other and this project agrees with none of them: it mints a fifth canonical that has never existed.

There is a second-order effect worth knowing about. The writer inherits version and date from the existing UTG file by matching on the table number in the file name, and UTG's files for three of these are named vs-v2-notAllCodes-NNNN.xml. The match fails, so those three inherit nothing and fall back to the default version — which means three of the “16 resources UTG does not have” are resources UTG has all along, under a name the parser did not recognise. Table 0347 is currently emitted at version 1.0.0 where UTG publishes 2.0.0.

A separate pair, 0567 and 0568, print another table's value set canonical — v2-0929 and v2-0930 respectively. Both the printed and the generated canonical exist in THO, so this is not a dangling reference; it is the value-set counterpart of the pattern ADR-0008 D11 found for code systems, where one table borrows another's terminology. It needs the same treatment and has not had it.

None of this has been changed. Honouring the printed URI is not a blanket rule — a page URL and a permalink are not canonicals, and adopting them would be worse than ignoring them. It needs the same classify-then-resolve treatment the Code System URI already has, and that is a decision rather than a fix.

Completeness check
